# Pull Request 管理规范

PR 应从问题到结果逐层展开，让审阅者先理解目标，再验证实现，最后判断发布风险。默认使用仓库的 `.github/pull_request_template.md`，不要删除不适用章节，填写“不适用”并说明原因。

## 标题

使用 `type(scope): 中文结果`：

- `feat(home): 完成燕中系开屏与首页连续转场`
- `fix(auth): 修复内部口令注册审核状态`
- `docs(ops): 更新 staging 与验收流程`

`type` 使用 `feat`、`fix`、`refactor`、`test`、`docs`、`chore` 或 `ci`；`scope` 使用稳定业务域，不使用人名、日期或“杂项”。标题描述用户或系统得到的结果，不罗列文件名。

## 描述顺序

1. 目标与背景：问题、受影响用户、成功标准和明确边界。
2. 变更层级：先基础设施与共享契约，再业务流程，最后界面表现。
3. 验证证据：给出实际命令结果、视口、主题、语言和业务状态，不只写“已测试”。
4. 数据与安全：说明 migration、seed、缓存、限流、密钥和个人信息影响。
5. 风险与回滚：列出可观测信号和最短恢复路径。
6. 外部依赖：域名、邮件、OAuth 凭据等不能在仓库内完成的事项单独列出，不与代码完成度混写。

## 范围控制

- 一个 PR 只承载一个可叙述目标；共享底座可以和直接消费者一起提交。
- 不混入格式化噪声、测试报告、临时截图、数据库、上传文件或本地环境配置。
- 删除文件前用引用搜索、构建和测试确认无消费者；一次性修复脚本完成使命后不得长期保留。
- UI PR 必须覆盖 1440×900 与 iPhone 13 等效视口、暗亮主题、中英文和 reduced motion 的相关路径。
- 认证、数据或部署 PR 必须说明失败模式，不能把本地模拟通过写成真实外部服务已打通。

## 合并门槛

至少执行 `npm run release:check`。涉及页面和交互时再执行 Playwright；涉及 Compose 时确认 `/api/health` 的 database 与 redis 均 connected；涉及完整业务流程时执行隔离环境的 `npm run test:acceptance`。
